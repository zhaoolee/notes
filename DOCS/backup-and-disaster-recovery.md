# 备份与灾难恢复方案

## 1. 目标与结论

本方案面向以下故障：生产主机损坏、代码仓库或镜像仓库被删除、线上文件被篡改、
管理员账号被盗、错误发布破坏数据，以及第三方服务配置丢失。

推荐采用“后台手动导出 + 自动异地备份 + 发布恢复工件”三条链路：

1. 超级管理员后台提供“导出完整灾备包”，用于发布前、重大变更前和人工留档。
2. 服务端按固定周期生成加密数据快照，并写入与生产环境隔离、开启不可变保留的
   对象存储。手动下载不能代替这条自动链路。
3. 每次发布由可信构建流水线生成与精确 Git commit 对应的源码包、构建清单和可选
   OCI 离线镜像包；生产服务只能读取这些工件，不能访问 Docker Socket。

建议的首期恢复指标：

- RPO（最多丢失的数据）：1 小时；生产发布前的人工快照 RPO 接近 0。
- RTO（恢复服务时间）：有公网依赖时 2 小时；使用完整离线镜像包时 4 小时。
- 备份保留：小时快照 7 天、每日完整备份 30 天、每月备份 12 个月、最近 10 个
  正式发布恢复工件。

这些指标应在首次完整恢复演练后按实测结果修订。

## 2. 当前系统的数据边界

### 2.1 必须备份的核心数据

| 内容 | 当前位置 | 恢复价值 |
| --- | --- | --- |
| 账号、scrypt 盐和密码哈希、密码版本 | `storage/data/notes-data.json` | 保留普通用户账号和登录能力 |
| 普通用户及超级管理员云工作区 | `storage/data/notes-data.json` | 保留便签、文件夹、星标、置顶和回收站 |
| 匿名上传额度状态 | `storage/data/notes-data.json` | 保持限额计数连续；丢失时也可安全重置 |
| 导入图片、页脚图片和导出文件 | `storage/images` | 保证便签中的站内 `/images/*` 引用可恢复 |
| 精确发布源码和构建方法 | 发布恢复工件 | 在仓库和镜像仓库均不可用时重建服务 |
| 服务端有效配置与 Secret | 运行时环境变量或 Secret 系统 | 恢复管理员登录、Cookie 签名、七牛和 AI 能力 |

当前 `storage/images` 混放用户导入图片与可重新生成的 PNG 导出物，无法可靠区分
哪些文件可以丢弃。首期完整备份必须包含整个目录。后续应拆分为
`storage/assets` 和带生命周期的 `storage/exports`，再让增量备份只长期保存前者。

### 2.2 必须备份的代码恢复工件

源码恢复包应由发布流水线从干净工作区的精确 commit 生成，而不是在请求导出时从
GitHub 临时下载。恢复包至少包含：

- `git archive <commit>` 生成的完整已跟踪源码快照；
- `package.json`、`package-lock.json`、TypeScript/Vite 配置；
- `Dockerfile*`、`docker-compose*.yml`、`docker/`；
- `src/`、`server/`、`public/`、`example/`、`scripts/` 和 `skills/`；
- `frontend/tests/`、`backend/tests/`、`DOCS/`、`PROMPTS/`、`TOOLS/`；
- 发布 commit、tag、构建时间、Node/Playwright 基础镜像和最终镜像 digest；
- `npm test` 与 `npm run build` 的结果摘要；
- 一份不依赖线上站点的恢复操作手册。

`.env`、`storage/`、`node_modules/`、`dist/` 和 `.git/` 不进入源码快照。完整 Git
历史可额外用 `git bundle --all` 保存到独立的发布工件库，但恢复当前服务只需要
精确源码快照。

只保存源码和 lockfile 仍依赖 npm 与基础镜像仓库。需要断网恢复时，发布流水线还
必须生成签名的 OCI 镜像归档和对应的恢复 Compose 文件。OCI 工件通常较大，建议
保存在独立工件库；管理员后台只有在它被只读挂载到
`RECOVERY_ARTIFACT_DIR` 时才允许把它加入下载包。禁止为此给 Web 后端挂载
`/var/run/docker.sock`。

### 2.3 服务端无法覆盖的数据

- 匿名用户的 `notes.workspace.v1` 只存在于各浏览器 `localStorage`，超级管理员
  无法从服务端导出。需要为匿名用户另做“导出个人工作区”功能，或提示登录后同步。
- 页脚文案、页脚 Logo、主题和 AI 开关目前主要保存在浏览器本地，不属于
  `NoteWorkspace`。如果这些设置被定义为核心用户数据，应先迁移为服务端账号设置。
- Markdown 中的任意外站 URL 不受本系统控制。站内 `/images/*` 可随本地图片目录
  恢复；七牛长期对象应在七牛侧开启版本保护或跨账号复制；其他外站图片只能记录
  URL，不能承诺灾后仍然存在。
- DNS、TLS 证书、宿主机反向代理和 GitHub/Docker Hub 权限不在当前应用目录内，
  必须由基础设施清单和对应平台的独立备份覆盖。

## 3. 灾备包格式

推荐文件名：

```text
notes-full-<UTC时间>-<release短SHA>-<backupId>.tar.gz.age
```

使用 `age` 公钥加密整个 `tar.gz`。生产环境只保存一个或多个 age recipient 公钥，
私钥离线保管在至少两个不同位置。下载到浏览器的始终是密文；没有配置
`BACKUP_AGE_RECIPIENTS` 时，生产环境应禁用完整导出，不允许回退为明文 ZIP。

解密后的目录结构：

```text
manifest.json
data/notes-data.json
media/images/...
release/source-<full-commit>.tar.gz
release/release-manifest.json
release/release-manifest.sig
release/oci/                         # 可选，存在离线工件时才包含
config/runtime.env                   # 位于整体密文内，仅包含白名单变量
config/external-services.json        # 桶、域名、镜像与依赖标识
runbook/RESTORE.md
```

`config/runtime.env` 只允许写入明确白名单，例如 `SUPERADMIN`、
`SUPERADMINPASSWORD`、`SESSION_SECRET`、`ANONYMOUS_DAILY_UPLOAD_LIMIT`、
`QINIU_*`、`OPENAI_*` 和 `WECHAT_FOOTER_HAMMER_URL`。不得序列化整个
`process.env`，以免把宿主机、云平台或 CI 的无关凭据带入备份。

`manifest.json` 至少包含：

- 备份格式版本、备份 ID、创建时间、来源实例 ID；
- 数据 schema 版本、账号数、工作区数、图片数和总字节数；
- release commit、tag、镜像 digest、源码工件 digest；
- 每个归档成员的相对路径、大小和 SHA-256；
- 是否包含 Secret、源码、OCI 镜像和第三方对象清单；
- `offlineRestorable` 布尔值及仍需联网获取的依赖；
- 快照开始/结束时间以及创建过程中产生的警告。

归档中每个文件都做 SHA-256 校验。发布流水线使用独立的 Ed25519/Cosign 密钥签署
`release-manifest.json`，使恢复人员能确认源码和镜像确实来自可信发布流水线。
数据清单哈希用于发现传输和存储损坏；如果生产服务本身已被完全控制，不能仅凭它
自行生成的哈希证明数据未被恶意修改，必须结合不可变历史备份和事故时间线选择
可信恢复点。

## 4. 一致性快照方法

当前 `NotesDataStore` 通过单进程队列和原子重命名写入 `notes-data.json`。备份实现
应增加一个同样进入该队列的 `createSnapshot()`：

1. 在写队列内读取并解析当前数据库；解析失败立即终止备份。
2. 把标准化 JSON 写入权限为 `0600` 的快照文件并 `fsync`，记录数据时间点。
3. 释放写队列；锁只覆盖小型 JSON 快照，不覆盖图片压缩过程。
4. 枚举 `storage/images` 中的普通文件，拒绝符号链接、硬链接逃逸、设备文件和任何
   越过根目录的路径。
5. 流式读取并计算图片哈希；若读取前后大小或修改时间变化，则重试或使任务失败。
6. 校验所有工作区中的站内 `/images/*` 引用都在快照文件列表中。缺失引用默认使
   “完整灾备包”失败，而不是只产生警告。
7. 流式完成 `tar -> gzip -> age`，不在磁盘上生成包含 Secret 的明文中间包。
8. 再次读取最终密文并计算 SHA-256，成功后用原子重命名发布下载文件。

图片保存先于工作区引用写入，且当前没有覆盖已有图片的流程；采用“先锁定 JSON、
后枚举全部图片”的顺序，可以容忍备份期间的新上传：最多包含少量尚未被快照引用的
新图片，不会漏掉快照已经引用的站内图片。

生成前检查临时目录剩余空间，建议至少为预计密文大小的 1.5 倍。归档必须全程
流式处理，不可把整个 `storage/images` 或最终下载一次性放入 Node.js 内存。

## 5. 超级管理员后台设计

在 `/superadmin` 增加“灾备与恢复”区域，显示：

- 当前 release commit/tag 和构建时间；
- 数据文件是否可解析、账号数、工作区数、图片数和估算大小；
- age recipient 指纹、源码工件和 OCI 离线工件是否就绪；
- 最近一次自动备份、最近一次恢复演练和结果；
- 任务历史只显示时间、范围、大小、校验值和结果，不显示 Secret 或便签正文。

提供两个动作：

1. **导出完整灾备包（推荐）**：数据、所有图片、精确源码、构建清单、白名单配置、
   恢复手册，以及可用时的 OCI 工件。
2. **导出数据快照**：只包含数据、所有图片、清单和恢复手册，用于发布前快速留档。

创建任务前弹窗必须展示范围、预计大小、加密 recipient 指纹和到期时间，并要求
超级管理员重新输入当前密码。不能只依赖已有 Cookie。

任务采用异步状态机：

```text
queued -> snapshotting -> hashing -> packaging -> encrypting -> verifying -> ready
                                                                    -> failed
```

前端轮询状态并显示当前阶段。就绪后显示下载按钮、密文 SHA-256、大小和过期时间。
临时密文默认在首次成功下载后 1 小时或创建后 24 小时清理；进程重启时也应扫描并
清理过期文件。失败任务删除所有临时文件。

首期不要在后台提供“上传并恢复”按钮。恢复会覆盖线上状态，必须在干净主机上通过
命令行工具完成预检、停写、二次备份和原子切换。

## 6. 管理端 API 草案

所有接口都要求 `superadmin` 会话、`Cache-Control: no-store`，并禁止跨 Origin
写请求。

```text
GET  /api/superadmin/backups/capabilities
POST /api/superadmin/backups
GET  /api/superadmin/backups/:backupId
GET  /api/superadmin/backups/:backupId/download
```

`POST /api/superadmin/backups` 请求示例：

```json
{
  "scope": "full",
  "password": "仅用于本次重新验证，不持久化",
  "includeOciImages": true
}
```

安全要求：

- 管理员密码只参与当前请求的常量时间校验，不进入任务参数、日志或审计正文；
- 重新验证成功状态只对当前管理员会话短暂有效，例如 10 分钟；
- 同一时间只运行一个完整备份任务，并限制创建频率和失败重试；
- 下载任务绑定创建它的管理员身份，不使用长期公开 URL；
- 下载响应设置 `Content-Disposition: attachment`、`nosniff` 和 `no-store`；
- 日志只记录管理员、时间、来源 IP、范围、backup ID、结果和密文哈希；
- 错误响应不能包含路径、环境变量值、便签正文或外部服务错误原文；
- 临时目录固定为专用根目录并设置 `0700`，任何归档路径都必须经过规范化；
- 不允许客户端传入任意文件路径或要打包的目录。

建议将成功/失败审计同时发送到生产主机之外的日志系统。只写本机的审计记录无法抵抗
主机被完全控制的情况。

## 7. 自动备份与 3-2-1 保留

后台导出解决“管理员此刻拿走一份”的需求，但攻击者通常会优先删除生产主机上的
备份，因此还应设置：

- 每小时：`notes-data.json` 加密快照；
- 每日：核心数据和全部图片的完整加密包；
- 每次发布前后：完整数据快照和发布恢复工件；
- 每月：把一份已验证备份复制到离线介质或第二云账号。

至少保留三份副本、两种介质、一份异地/离线副本。对象存储位于与生产不同的云账号，
开启版本控制和 Object Lock/WORM。生产侧凭据只允许新增对象，不允许删除、覆盖、
缩短保留期或读取历史备份。即使攻击者拿到生产凭据，也只能写入新的可疑备份，不能
删除事故发生前的可信版本。

七牛长期对象单独开启版本保护或跨账号复制，并定期保存对象 inventory。不要让应用
主机持有可以清空源桶和备份桶的同一组高权限密钥。

## 8. 恢复流程

恢复工具建议放在 `scripts/restore-backup.mjs`，并随源码恢复工件与备份包一起保存。
工具默认只做验证，只有显式 `--apply` 且目标目录为空或已经二次备份时才写入。

### 8.1 选择可信恢复点

1. 隔离被攻击的主机，保留磁盘和日志，不直接在原机覆盖。
2. 根据事故时间线选择攻击发生前最后一份校验成功的不可变备份。
3. 在离线环境用 age 私钥解密；核对外层密文 SHA-256、全部成员哈希和发布签名。
4. 检查 `offlineRestorable` 和缺失依赖，不把“只含源码”误当成完整离线恢复包。

### 8.2 在干净主机恢复

1. 安装受支持版本的 Docker/Compose，或导入备份中的 OCI 镜像。
2. 解开源码快照，确认 commit、lockfile 和构建清单一致。
3. 从备份白名单配置创建新的 `.env`，设置 `0600`；事故场景优先轮换
   `SUPERADMINPASSWORD`、`SESSION_SECRET`、七牛、OpenAI、GitHub 和镜像仓库
   凭据。轮换 `SESSION_SECRET` 会使所有旧 Cookie 失效，这是期望行为。
4. 把 `storage/data` 和 `storage/images` 恢复到新的临时目录，拒绝符号链接和路径
   穿越，校验 JSON schema、文件数量、大小、哈希和所有站内图片引用。
5. 保证后端尚未启动，再原子切换两个目录；`notes-data.json` 设为 `0600`。
6. 有网络时从源码执行 `npm ci`、`npm test`、`npm run build` 和
   `docker compose build`；离线时加载已签名 OCI 归档并使用恢复 Compose。
7. 只启动一个后端写入实例，验证本机 `/api/health` 后再接入反向代理。
8. 使用专用恢复测试账号验证登录、工作区、站内图片、PNG、ZIP、公众号和 AI；
   不修改真实用户内容。
9. 切换 DNS/流量，监控错误率和存储写入。保留旧环境只读副本直至确认恢复成功。

不得在运行中的唯一后端实例上直接覆盖 `notes-data.json`。任何数据回退前都要再次
备份当前状态，以便在选择了错误恢复点时撤销操作。

## 9. 校验与恢复演练

没有恢复演练的备份只能算“可能可用”。建议每月自动在隔离临时目录执行一次数据
恢复，每季度在全新主机执行一次完整服务恢复。

必须覆盖的 feedback 测试：

- 非管理员、普通用户和过期管理员会话都不能创建或下载备份；
- 已登录管理员未重新输入密码时不能创建；跨 Origin 请求被拒绝；
- 备份期间并发保存工作区，恢复结果对应一个完整时间点，不出现半写 JSON；
- 包含中文名、超大图片和大量小文件时仍保持流式处理和稳定内存；
- 符号链接、硬链接、`../`、绝对路径和设备文件不能进入或逃出归档根目录；
- 修改密文或任一解密文件后，校验必须失败；
- 缺失站内引用图片时“完整灾备包”失败并给出不泄露正文的错误；
- Secret 不出现在源码包、接口 JSON、日志、前端状态或未加密临时文件中；
- 任务失败、下载完成、超时和进程重启后，临时文件都按策略清理；
- 从空目录恢复测试 fixture 后，账号隔离、密码版本、工作区、图片和健康检查正常；
- 源码包能在干净环境通过 `npm ci`、`npm test` 和 `npm run build`；
- OCI 离线包在断网环境可启动并通过核心 smoke test。

## 10. 分阶段实施建议

### 阶段一：可验证的手动完整导出

- 在发布流水线生成并签署精确源码恢复工件；
- 增加数据快照、manifest、流式归档和 age 加密模块；
- 增加超级管理员重新验证、异步任务、状态与下载 UI；
- 提供只读的验证/恢复 CLI 和端到端恢复测试；
- 完整备份暂时包含全部 `storage/images`。

### 阶段二：自动异地不可变备份

- 接入独立账号对象存储、版本控制、WORM 和只写凭据；
- 实现小时/每日/发布前备份策略、保留清理和外部审计；
- 增加备份监控：最后成功时间、时长、大小突变、校验失败和恢复演练时间。

### 阶段三：提升规模与完整离线能力

- 拆分用户资产和可再生导出缓存，图片按哈希做增量备份；
- 为七牛长期对象建立跨账号复制和 inventory 校验；
- 把账号本地偏好迁移进服务端用户设置；
- 生成并异地保存多架构 OCI 离线包、SBOM 和供应链签名；
- 数据量或后端副本增加前，将单 JSON 存储迁移到支持事务和 PITR 的数据库。

## 11. 验收标准

方案实施完成的判定不是“后台出现了下载按钮”，而是同时满足：

1. 管理员可以下载一个仅用离线私钥才能解密的完整灾备包。
2. 灾备包包含指定时间点的全部服务端账号/工作区、全部站内图片、精确源码、构建
   清单、恢复手册和明确的联网依赖声明。
3. 生产主机或 GitHub/Docker Hub 全部不可用时，仍至少有一份独立账号中的可信数据
   备份和发布工件；若声明 `offlineRestorable=true`，断网恢复也必须实测成功。
4. 自动校验可以发现内容损坏、缺图、错误源码版本和路径攻击。
5. 每季度从零恢复成功，并记录实际 RPO/RTO、问题和改进项。
